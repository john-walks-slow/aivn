# 回到旧轮走原路：继续按钮的复用闸门太窄 排查

**状态：已定位、已复现、已修（worktree `fix/revisit-old-path`，基线 `0da3c2aa`）。** 2026-10-10 用户报告。

## 现象（用户原话）

> 跳转到过去的节点，然后继续到那个 beat 结尾，就会变成再点一下又生成出新的分支。
> 预期是除非选了不同选项，应该继续走过去的分支的啊。

用户后续的两句澄清（决定了修复面）：

> 我遇到的是〔跳开端卡再按继续〕。
> 以及就算不是跳开端，一路点继续走到某轮末尾，再点继续就新写了一拍……**和插一句没关系，我没插一句也会这样**。

即：**不跳开端也会复现**，且**不是插一句专属**。

## 根因

「回到旧轮走原路」只有一处实现：`orchestrator.revisitOldPath()`（`apps/server/src/orchestrator.ts`）。
它在**生成之前**查树上有没有现成的下一拍，有就走进去、不生成。而它有三道闸门：

```ts
if (!anchor || anchor.kind !== "beat_end") return false;         // 闸门一：挂载点必须是 beat_end
const key = resolved ? `input:${resolved.text}` : "continue";    // 闸门二：动作与子节点的来源标签逐字相同
const candidates = tree.childrenOf(anchorId).filter((child) => originOfBeat(child) === key)…
// 闸门三：beatEndFrom(child) 见岔口（子节点不唯一 / 下一个是 fork 标记）就停在岔口处
```

三道都过窄，各自对应一类「玩家明明在走原路、引擎却当新走向」的入口：

| # | 玩家的操作 | 被哪道挡下 | 现在的行为 |
|---|---|---|---|
| ① | 路线图点「开端」卡的**跳转**（回到故事起点），再点继续 | 挂载点 = `root`，不是 `beat_end` → 闸门一 | 从零**新写一整枝**（root 下多出第二个孩子） |
| ② | 跳回某一轮末尾后点继续，而**那一轮的下一轮原本以插一句 / 选项开头** | 子节点的来源标签是 `input:（那句话）`，本次动作是 `continue` → 闸门二 | 又**新写一拍**，旧的那一拍被顶成兄弟枝 |
| ③ | 一路点继续往前走，走到某一拍**内部曾经分岔过**（重写落在拍内）的那条链上 | `beatEndFrom` 停在岔口 → 落点停在拍中间；下一次按继续挂载点不是 `beat_end` → 闸门一 | 就地**新写一拍**（旧拍的后半截被顶成分支） |

三类的共同点：**玩家按下的是「继续」，没带任何新意图，本该沿旧路走**。
闸门一把「轮边界」等同于「beat_end」，于是起点被拒；闸门二把「继续」也当成一种需要逐字匹配的输入；
闸门三让落点停在拍中间，等于把 ③ 的玩家交给闸门一。

## 用户那句「和插一句没关系」怎么解释

③ 就是不依赖插一句的那条路，而且它在真实存档里留了指纹（见下）。
①②③ 之外没有第四条：`revisitOldPath` 是唯一的复用入口，`playerAction` 里那一次调用点之后就是生成。

## 复现

`apps/server/test/zz-scratch.test.ts`（诊断期临时用例，已并入正式用例）：

```
① 跳 root → 继续：模型被调用，leaf 落在新枝上（期望不调模型、落到第一拍末）
② 插一句开头的下一轮 → 跳回该轮末 → 继续：模型被调用，leaf 落在新枝上（期望走回旧的那一拍）
③ 拍中岔口 → 从上一拍末尾按继续：落点停在岔口处那句（期望落到 beat_end）
```

真实存档佐证：

- **`plays/testtest`（今天 04:30 仍在写）**：root 下有两个孩子——老的 `preload` 枝（10-07）与新的 `scene` 枝（10-10 04:30）；
  `prevLeafId` 指向**老枝末梢**（正是跳回起点之前世界线所在的位置）。这就是①的指纹。
- **`plays/test`（10-05 01:12 写过）**：`emutly1lx-6x`（narrate）底下有三个孩子——
  beat_end（10-04 09:17，原本的收束）、fork（10-04 09:21，重写）、scene（10-05 01:12，玩家又点出来的一拍）。
  从上一拍末尾按继续时，`beatEndFrom` 在岔口停下 → 落点是这个 narrate → 再点继续就生成了那个 scene。
  这就是③的指纹，全程**没有插一句**。
- **`plays/320000`（今天 06:19 写过）**：59 个 beat_end、0 个 stop，一条直链；
  其中 **4 个 beat_end 的继续是死路**（下一轮以 `prompt`（插一句）开头）：`emuyk3xk6-sb` / `emuykor8h-13v` /
  `emuykwupj-1dg` / `emuyqsp8j-2ns`——②的指纹。

## 现象与根因的关联

玩家的期望（原话）是「除非选了不同选项，应该继续走过去的分支」——即**分叉的唯一触发是「选了不同选项」**。
现在实际的触发面比这大得多：只要旧路的下一拍不是「无输入地继续」长出来的（以插一句 / 选项开头），
或者挂载点是起点，或者旧路在拍中间岔过，按继续就分叉。玩家看到的就是「再点一下又生成出新的分支」。

## 修复（已实施）

改一处判据 + 一处原语，不动别的动词：

1. **锚点认轮边界**：`beat_end` 或 `root`（起点也是边界，哨兵卡「跳转」落的就是它）。①由此修好。
2. **来源标签只对带输入的动作逐字匹配**（选项 / 自由输入，选同一个走原路、选不同才分岔）；
   **「继续」不带意图，不按来源标签筛**——多条候选里仍按「最后去过的那条」（`prevLeafId`，现有 `lastVisited`）挑。②由此修好。
3. **`LineageTree.beatEndFrom(head, prefer)` 见岔口顺着这条世界线走**（`prefer` = `prevLeafId` 落在谁的子树里就走谁；
   否则优先 `beat_end` 孩子，再否则最早落笔的非 fork 孩子），不再原地刹车。③由此修好——
   落点因此总是一个 `beat_end`，不会再停在拍中间。空壳 fork（子树被剪光）仍返回 `null`（那条枝不是一拍）。
4. **`prevLeafId` 传进 `beatEndFrom`**：拍中岔口上因此跟着「上次走过的那条世界线」走，而不是随便挑一条。

## 未纳入本次修复的边界（如实记录）

**跳到「被轮中分叉切在半路」的那张卡片再按继续，仍然会生成新的一拍。** 那条路的锚点确实在拍中间，
而现在仍然保持「轮中被锚定不认旧路」这条既有语义（旧注释与旧用例都把它写成故意的：
那时子节点是本轮的下一句，认了会把「继续」接回自己这一轮的后半截）。
③ 修好之后，这种半路卡片只可能来自「重写锚在拍中」的历史数据，新流程不再产生。
真要改，是产品语义的一次变更（继续 = 把这一拍读完 vs 就地重开），需要用户单独拍。

## 置信度

- ①②③ 的复现、根因与修复：**高**（三份用例 + 三份真实存档双向对上；修复后用例全绿、既有的 130 条谱系用例无回归）。

## 验收标准

1. 跳开端卡「跳转」→ 继续：不调模型，落到第一拍末节点（走原路）。
2. 一路点继续走到某轮末尾 → 再点继续：不调模型，走进旧路的下一拍（以下一拍是否以插一句 / 选项开头都不影响）。
3. 旧路在拍中间岔过（重写落在拍内）时按继续：不调模型，落点是 `beat_end`（不停在半拍上）。
4. 回归：选同一个选项仍走原路、选不同选项仍分叉、排队里有待注入的引导仍不认旧路、判废退回不进半拍。
