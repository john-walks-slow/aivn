# 后台记忆整理员 · 设计评估

日期：2026-10-04 · 分支：`main`（未开工，本轮只评估）
外部对照：`docs/freeform/261004-longform-memory-sota.research.md`（机制 5 = 异步记忆写手）、
`docs/freeform/261004-background-memory-agent.research.md`（本轮另做的一份聚焦调研）

**结论：可行，工程不是瓶颈。** 需要的管道已有八成（转录渲染、单发 LLM 调用、白名单写口、轮边界重建、
在生成物记账）。真正的难点是语义：整理员的素材来自**某一条分支**的演出，而它想写的 `memory/index/`
是**剧目级、跨分支共享**的——「哪些东西够格升级成剧目正典」这件事现在没有答案，写得越多泄漏越多。
建议先做零代码实验，再做一个把产物收窄到「存在性/身份」类的形态 A。

## 现状：今天谁在写记忆

| 层 | 位置 | 分支语义 | 谁在写 |
|---|---|---|---|
| 常驻 | `memory/always/`（premise / craft / nsfw） | 剧目级，跨分支共享 | 用户、工坊 |
| 索引 | `memory/index/**`（标题+一句话摘要每轮注入 A 区） | 剧目级，跨分支共享 | 剧作家（通用 `write`/`edit`）、工坊、用户 |
| 角色 | `characters/<id>.md` | 剧目级 | 剧作家、工坊、`generate_image` 自动建最小卡 |
| 纪元 | `memory/arcs/<arcId>.md` | **分支级**，按 `arcIds` 过滤 | 引擎（纪元压缩） |
| 切片 | `memory/archive/events.jsonl` | **分支级**，按 `tree.pathSet()` 过滤 | 引擎（逐轮 800 字原文，无 LLM） |

- **引擎已经做过一次「自动记忆」**：`orchestrator.ts:1722` 的 `maybeCompactEpoch`，在轮边界同步跑一次
  `completeText`（`compaction.ts` 的 `EPOCH_SUMMARY_SYSTEM` + `renderTranscript`），产物是 arcs 卡，
  然后重建 Agent。这是整理员最直接的模板：一次调用、结构化输出、失败只告警不阻断。
- **A 区在纪元内冻结**，任何一次写卡都要走 `PlayEnv.writeFile → onPlayFilesChanged →
  playhouse.onPlayFileWritten → rebuildAtBeatBoundary`，而重建 = 换编排器 = A 区重写 = **整段前缀缓存清零**
  （长剧目一次几万 token）。所以「剧作家随手写卡」的真实代价比看上去高；按纪元边界批量落卡反而更省
  （那一刻本来就要重建）。
- **没有调度基建**：全仓没有 `setInterval`，没有后台任务模型，只有去抖/超时用的零散 `setTimeout`；
  `pendingJobs` 只负责记账和 UI 显示。任何「空闲时跑」「每 N 轮跑」都是要新写的机制。

## 三个候选形态

| 是什么 | 压缩那次调用的产物扩成「arcs 摘要 + index 卡」 | 独立的 one-shot LLM 任务，按 N 轮/空闲触发，无工具 | 像工坊那样一条独立 agent 通道，装 `read`/`write`/`edit` |

## 可行性

- 已有：转录渲染（`renderTranscriptAs` 已支持不同读者视角）、单发调用（`completeText`，但 `MAX_TOKENS = 2048`，
  多卡输出要另开上限）、写口收口（`PlayFiles.write` 一份白名单）、轮边界重建、在生成物记账、记忆页
  （`MemoryPane.tsx`）本来就把卡摆成卡片、用户能手改——**整理结果天然可看可改，不需要新的审阅界面**。
- 缺的：触发调度、幂等/去重策略、产物边界（见风险 1）、整理这件事的可观测性。
- 外部对照（已有调研的结论，此处不重复论证）：Letta 的 sleep-time agent / dreaming 正是这个形态——主张把
  记忆管理从主 agent 卸载，触发可选「每 N 个 step」或「上下文被压缩时」，**可用更强更慢的模型**（不受延迟约束），
  可选 `Agent reviews before applying` 二次审阅，另有 `/doctor` 审计重复与 token 占用；AI Dungeon 的记忆
  由另一个模型并行写；Mem0 的写入策略保守（`NOOP > DELETE > UPDATE > ADD`）。同时 SOTA 界**没有**解决
  有界记忆——别把整理员当成长程一致性的解药。

### 本轮调研补进来的四条（`docs/freeform/261004-background-memory-agent.research.md`）

1. **「后台」这个属性本身没有被证明有价值**：没有任何系统或论文做过「异步整理 vs 同步整理」的头对头对照。
   有量化收益的都是**整理的产物质量与契约**（Microsoft 的环境探测式策展 arXiv 2609.11060：给既有 curator
   加只读世界工具后 pass rate 39% → 73%，task-agent 成本 $3.38 → $1.68），不是「跑在后台」。据此，
   形态 A（挂在纪元边界、同步）应当排在形态 B/C 之前：不影响契约，白拿调度。
2. **失败模式有名字也有一份对照清单**：同一篇论文点名 curator 会「保留错误、**过度一般化局部证据**、保留过期知识」；
   这正是本仓要防的三件事。同场景的参照实现是 SillyTavern 的 Smart Memory（11 个 tier、**独立 Memory LLM
   与扮演模型分开跑、互不争抢**、embedding 去重、两遍式取代检测）——可直接当需求清单逐条对照。
3. **触发参数有现成的默认值**：AI Dungeon 每 6 个 action 摘要一次、首次在第 12 个 action、**最近 6 个 action
   永不摘要**（所以还能自由编辑撤销）。最后这条尤其值得照抄：整理范围不该碰到「还在手上的那几拍」。
4. **反面证据要摆在桌面上**：记忆系统放大谄媚最高 25×（Writer, 2026-06）；反思性记忆**强化错误信念**而非纠正
   （Honest Lying, ICML 2026，121 条反思 0 条提及正确目标）；HaluMem 测出现有系统在抽取阶段累积幻觉；
   AuthMem-Bench 的 49 个配置里 48 个出现 **authority collapse**（保留内容、抹掉来源限定），
   补上权威标签后未授权动作率 16.9% → 0.0%。所以整理员的第一原则是**只抽取、不反思、不推断**——
   与 `EPOCH_SUMMARY_SYSTEM` 里已有的「只复述原文已有的事实」同一条。
- **动手前先做一个零代码实验**：拿一份真实剧目的 `archive/events.jsonl` 或 `lineage.jsonl`，手工跑几遍整理
  提示词，量三个数：抽出多少条、其中多少条是幻觉/过度一般化、跨分支看多少条构成剧透。半天成本，能直接
  决定这件事值不值得写代码。

## 风险点（按严重度）

1. **分支剧透泄漏（最硬的一条）**。`index` 是剧目级、跨分支共享（`memory.ts:87-93` 明写这是设计），
   而整理员的素材是分支级的。A 分支里「小春是凶手」被揭示 → 整理员写进 `lore/` → 切到还没演到的 B 分支，
   这张卡每轮注入 A 区 = 直接剧透。arcs/archive 的按分支过滤正是为挡这个而建的，整理员会把它从 index 侧绕开。
   这不是假想：VS Code 的 issue #307617 就是记忆文件不跟 checkpoint 回滚造成的
   「logic persistence」循环，原话是「如果记忆持续存在，『恢复检查点』就失去主要效用」。
   学术侧的答案已经有形状——RIR（arXiv 2609.18304）把**分支局部状态**与**可复用知识**分开，
   规定任何字段都不表示 agent 当前状态，真值可能取决于被回滚动作时要保留溯源、标记待重验。
2. **NSFW 不变式**。限制级内容对全年龄读者的唯一出口是段末 SFW 摘要。整理员若在段内跑、或读到露骨原文
   写进 index，就破了这条不变式。压缩器靠 `if (this.nsfwActive) return` 挡着，整理员要照抄，且取料要走
   SFW 侧折叠视图（`rebuild.ts` 的 `lineageToBeats(…, { nsfw })`）。
3. **幻觉固化**。写进 index 的东西**每轮注入**、被当成世界事实，错一条会顺着往下演（ConStory 的「错误会聚集」）。
   手动写卡时作者知道自己为什么写；整理员只有转录，最容易把一次性细节过度一般化——Microsoft 那篇论文
   点名 curator 的三宗罪就是「保留错误、过度一般化局部证据、保留过期知识」。更糟的是**反思会强化错误**：
   Honest Lying（ICML 2026）里 121 条反思中 0 条提及正确目标；HaluMem 测出现有系统在**抽取阶段**就累积幻觉。
4. **无界增长 + 重复卡**。`indexSection`（`prompt.ts:397-403`）把全部可见卡铺成一行行的，**没有任何上限**；
   整理员每次看到重叠转录，倾向于换个名字再建一张。手动写卡天然自限，自动整理不自限。SOTA 的开放问题
   也在这里——「有界 + 不丢关键 + 可下钻」没有现成答案（可选组合：注入预算 + 硬上限 + 遗忘衰减）。
5. **三写者并发**。pi 的 `withFileMutationQueue` 是 **per-`PlayEnv`** 的（WeakMap），剧作家/工坊/整理员各持
   一份 env，互不串行；用户还能在文件页手改。整理员若做「读—改—写」，与别人重叠就是丢更新。现在只有
   `play.json` 有锁（`withPlayConfigLock`）。同类问题有真实事故：Hermes 的 flush agent 在**对记忆当前状态
   一无所知**的情况下写，静默覆盖了更新过的条目。业界的做法是两种——在 spawn 处设 single-writer gate
   （而不是在各自提示词里），或按内容摘要做乐观并发（Claude Memory Stores 的原语就是 `content_sha256`）。
6. **成本与网关争用**。整理员和演出共用同一个网关（cpa 有 429 前科）。它在玩家等戏的时候抢额度，伤的是
   最该保的那条路径。缓解：空闲才跑 + 与演出互斥（`whenIdle`）+ 独立（更便宜）模型档。
7. **丢掉 salience 信号**。剧作家写卡是带着写作意图的（「这个伏笔后面要用」）；整理员只有转录文本，
   埋得深的伏笔最容易漏，而漏掉的正是最该记住的。
8. **「不建议写」只是软规则**。收成通用工具之后，`write`/`edit` 对剧作家是全开的（写角色卡要用它），
   没有「只能写角色卡」的白名单——要实现硬边界就得在 `PlayFiles` 里加一张「角色 → 可写前缀」的表
   （一份白名单、两列，不是回到两份 id 清单），否则两处写者会长期共存并互相覆盖。
9. **不可回退**。剧目文件不进谱系、不随分支回滚（`update_state` 才回滚）。整理员批量改卡之后想后悔，
   没有「回到上一版」——文件页能手动改回来，但没有版本历史。调研里所有同类系统的共识是：整理能力最弱
   也要配一个回退位。成本最低的三种现成形态：Claude Dreams 是**输入 store 永不修改、产出一份全新 store**
   （不满意就直接丢弃），ChronoMem 是每次写入产 whole-memory 快照 + 自然语言 undo（回滚一致性 +10pp），
   Cursor 是后台生成的记忆保存前征求批准。
10. **可观测性缺位**。谁在本轮的 A 区里、哪条卡为什么被注入/为什么没有——现在没有这样的视图
    （AI Dungeon 的 Context Viewer、Letta 的 `/doctor` 是同类需求）。整理员一上线，「记忆里到底多了什么」
    就成了排障的第一现场。

## 先要把契约定下来（调研里最值钱的一条）

各家在「该写什么」上分歧很小，出事的地方几乎都是**整理产物与源之间没有契约**——authority collapse、
stale overwrite、回滚不一致、过度一般化，全是同一个根因。可复用的原语只有五个，整理员要一次定齐：

| 原语 | 落到 stage-ai |
|---|---|
| **溯源** | 每张自动写的卡记「来自哪条分支、哪几拍」（卡里已有 frontmatter 的位置） |
| **权威标签** | 卡上标「引擎整理 / 作者手写 / 工坊写」；整理员**不得改作者手写的卡**（AuthMem-Bench：补权威标签后未授权动作率 16.9% → 0.0%，良性成功率不变） |
| **失效契约** | 分支回滚 / 玩家改写过的那几拍，对应的自动卡标记待重验，而不是继续当事实注入 |
| **幂等键 + 消费游标** | 只处理到某个 beat 为止，成功才推进；失败不推进 = 下次重做（nanobot 那套，不需要重试队列） |
| **快照边界** | 整理前把 `memory/index/**` 存一份，回退一格是基本能力（ChronoMem / Claude Dreams 两种现成形态） |

## 建议的落地顺序

1. **先做零代码实验**（半天）：真实剧目转录上跑整理提示词，量幻觉率、重复率、跨分支剧透条数。
2. **先同步、别做调度**：没有任何证据支持「后台」本身有价值（无头对头对照），而形态 A 挂纪元边界
   白拿调度。整理范围照 AI Dungeon 的规矩——**最近几拍永不整理**（它定的是 6 个，且首次整理在第 12 个），
   还在玩家手上、随时可能重写的那几拍不产生记忆。
3. **形态 A + 收窄产物**：只允许「存在性/身份」类——把 `generate_image` 自动建的
   「（演出中临时引入，设定未补。）」角色卡补成完整卡，加地点/组织/规则这类设定卡；
   **剧情事实一律不写进 index**（它本来就该待在 arcs / archive）。只抽取、不反思、不推断。
4. 契约五项至少落**溯源 + 权威标签 + 幂等游标**三项，再谈独立角色、审阅位与回退。

## 要你定的三件事

- **产物范围**：只补角色卡 / 角色卡 + 设定卡 / 连剧情事实也接管（第三项我不建议）。
- **剧作家写口**：`MEMORY_RULES` 改成软建议（还在，但不鼓励），还是在 `PlayFiles` 里加一张「角色 → 可写前缀」
  的表做成硬边界。
- **触发时机**：跟纪元压缩走（零新基建，但早期剧目压缩不频繁）/ 每 N 轮（要新写计数与互斥）/ 演出空闲时。
