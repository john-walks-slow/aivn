# 素材生命周期契约 · 小结

> 需求背景见 `261008-aivn-dual-host.plan.md`；本文件是 P0-3（媒体生命周期）的实施记录。

## 做了什么

新增共享契约 `packages/core/src/play/assetLifecycle.ts`：一份图 / 一首曲子从「在生成」到
「进了素材表」经过哪些状态。独立版与 DSH 各有各的队列和存储，但**状态名与可走的转换只有这一套**。

真实状态是五个：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已受理、还在生成（独立版剧作家的后台排产） |
| `draft` | 产物在草稿区，**还不是剧目素材** |
| `adopted` | 已入库，是剧目素材了（唯一可被剧本引用的状态） |
| `expired` | 草稿过了保留期被清理。不是失败 |
| `failed` | 生成没成，**错因必须留住** |

**有意没有 `rejected`**（任务书里列了，核实后认定不该有）：没被挑中的候选不是被谁否决的，
它只是没人采用，静静躺到过期。记成一个状态等于让每个候选都欠一次显式否决，而用户「没选」
这个动作在界面上根本不存在。

## 契约撞出来的一个真缺口

先写实现侧边界测试（`apps/server/test/assetLifecycleContract.test.ts`，从「实现真实走的路径」
反查契约接不接得住），立刻抓到：契约第一版只写了 `pending → draft → adopted`，而独立版
剧作家的后台排产在队列里把 draft + commit 一次做完，外部观察到的是 **`pending → adopted`**
——这条边当时不存在。已补进表并加了 `cause: "commit"`。

这条也说明「按契约自己的语义断言」的测法有盲区：同一条表自己跟自己对，接不住真实路径的错
测不出来。两套测试分开写是有意的。

## 接入的消费者

- `apps/server/src/playAssets.ts` 的 `DRAFT_TTL_MS` 改为由 `ASSET_DRAFT_RETENTION_DAYS`
  推出，不再手写 `7 * 24 * 60 * 60 * 1000`。「候选能躺多久」是两边对用户说的同一句话，
  写在契约里才不会一边改了另一边不知道（有测试钉住这条不许退化回字面量）。
- `PlayAssets.commit` 的重复采用行为按契约钉住：`adopted → adopted` 是合法边，产出幂等
  （同一路径、台账仍一条），但 `replaced` 回执如实为 `true`（确实覆盖了上一次写的那份）。

## 已知边界

- 契约只定义**领域语义**：谁去跑、跑多久、存在哪、异步还是同步，仍归各自宿主。
  独立版可以继续异步排队，DSH 可以继续同步等待。
- 没有强行统一队列、传输与持久化，也没有为 DSH 造一份它当前没有的状态。
