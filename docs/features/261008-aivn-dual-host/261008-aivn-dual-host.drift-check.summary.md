# Agent 契约漂移检查（P0-4）

> 前置：`261008-aivn-dual-host.contract.md`（能力矩阵与工具元数据）、
> `261008-aivn-dual-host.media-lifecycle.summary.md`（素材生命周期）。

## 要解决的问题

提示词、工具描述、能力位三者的载体不同（persona 在 `prompt.ts` / 机制在工具 `DESCRIPTION` /
装配在 `agentkit`），但互相引用。**改了一边忘了另一边不会报错**——只会在某个实例上悄悄教
模型去调一个不存在的工具，或者让同一条契约同时存在两种说法。这类漂移靠人眼查不住，要有机器守卫。

## 做了什么

`scripts/check-agent-contract.mjs`，跑法 `pnpm check:agent-contract`。五项检查：

| 检查 | 拦的是什么 |
| --- | --- |
| 提示词点名的工具都在装配面上 | 能力位关着时提示词仍教模型去调 |
| 提示词不承载工具参数细节 | 同一份机制在 persona 与 DESCRIPTION 各写一遍 |
| 素材状态词只用共享契约那一套 | 各宿主自己发明状态名（如把「没人采用」说成 rejected） |
| 生命周期常量由共享契约推导 | 手写天数，两边对同一条承诺各说各的 |
| 能力矩阵与能力目录一一对应 | 新增能力只登了一边 |

检查器**只查能确定对错的关系**，不检查文风、不猜语义——那种检查会在改文案时反复假红，
然后被人加 `--no-verify` 绕掉。

## 首跑抓到的真实漂移（已修）

首跑不是全绿，抓到三处，性质都是「机制被写了两遍」：

1. `prompt.ts` 用散文解释 `spriteId` / `variant` / `framing` / `stature` 的默认值与取值，
   而 `imageTool.ts` 的 DESCRIPTION 已有同一份（还更全）。删散文，留一行指针。
2. `workshop.ts` 复述 `draftId` 的用法，`commitTool.ts` 的 DESCRIPTION 已写。
3. `prompt.ts` 在「管理角色」关着那一支里报参数名（`spriteId` / `title`），改说「按工具说明填」。

三处都不是消灭信息，是**把信息挪回它该在的那一层**：persona 讲何时用，DESCRIPTION 讲怎么填。
顺带把仓库既有的分层规约落成了可执行的守卫——此前只有一条测试钉着「不出现 `<call:generate_image`」，
管不住参数细节。

## 检查器自身的两个坑（已处理）

- **词边界**：`spriteIdOf`（标识符）被认成参数名 `spriteId`。加 `\b` 并把 TS 注释剥掉
  （注释是给开发者看的，不进提示词，不该被这条检查误伤）。
- **示例调用要放行**：`generate_image(kind="sprite", spriteId="xiaoyu", …)` 教的是调用约定，
  一行例子比十句散文有用（仓库既有测试就钉着 `variant="neutral"` 必须在提示词里）。
  拦截的是另一种——**用散文解释参数**。规则据此收窄成「具名参数调用行整行跳过」。

这条边界不是猜的：收窄前后各跑了一遍，并且**注入一处假漂移验证它真会变红**（把 `rejected`
写回提示词 → 该检查立即失败，还原后转绿）。守卫自己不可信的话，绿也没有意义。

## 有意不做的

- **不自动改提示词**。发现漂移只报告，怎么改是人的判断——脚本改文案会把语义改坏。
- **不做跨仓库逐字比对**。DSH 的 prompt 本就按 DSH 事实改写，逐字对齐是错的目标
  （见 `261008-aivn-dual-host.plan.md`：「减少无意分歧」，不是「消灭所有分歧」）。
  DSH 侧的对应守卫在 `dsh-aivn` 自己的 e2e 里。
- **没接 CI**。这台机器上全量构建会超时（ARM 手机），先做成可手动跑的命令；
  真要接 CI 时命令已经就位。
