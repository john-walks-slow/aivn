# 通用工具替代边界审计（P1-11）

> 判据来自本次工作的起点：用户要「减少定制，让 agent 使用更通用的工具，从而更灵活、又减少维护量」。
> 配套阅读：`261008-aivn-dual-host.plan.md`（两条线定位）、
> `docs/references/261009-cross-host-verification.md`（验证矩阵）。

## 判据

不追求删掉所有 AIVN 专用工具。逐个按这四条判：

| # | 判据 | 处理 |
| --- | --- | --- |
| 1 | 纯文件读写、查找、普通上下文读取 | → 用 `read` / `write` / `edit` / `bash`（本项目无 glob/grep 工具，走 `bash`） |
| 2 | 稳定、**不可由模型可靠推断**的领域规则 | 保留专用工具 |
| 3 | 外部 API、用户确认、审计、特殊 UI、不可逆副作用 | 保留专用工具 |
| 4 | 只是提示下一步做什么、或只是包裹普通文件操作 | 候选删除或合并 |

## 审计结果（独立版 24 个工具）

### 保留：判据 2（领域规则，模型推不出来）

| 工具 | 为什么 `read`/`bash` 替代不了 |
| --- | --- |
| `read_memory_detail` / `search_archive` | **带分支过滤**：只召回当前分支可见的历史，不会召回其他世界线。裸 `grep` 会把别条分支的剧情捞出来——那是错的设定 |
| `beat_done` | 轮收束契约（停止点形态），是演出循环的出口，不是文件操作 |
| `enter_nsfw` / `exit_nsfw` | 通道切换，改的是编排器状态与谱系标记 |
| `update_state` | 提议状态更新，走的是引擎的状态机而非写文件 |
| `recut_sprite` | 需要「抠底前留底原片」这个只有引擎持有的东西（`media-cache/sprite-sources/`）；重新出图是另一张画 |
| `commit_asset` | 草稿→素材的**生命周期转换**（写 `assets/`、补素材表、记台账、搬留底），四件事要原子地一起发生 |
| `validate` 类（`get_readiness`） | 复用引擎的 readiness 报告（premise/立绘/背景的就绪判定），不是数文件 |
| `list_saves` / `read_lineage` | 读的是谱系数据模型（周目/分支），且明确**只读**——改结构要用户去路线视图，模型没有写权限 |

### 保留：判据 3（外部 API / 确认 / 不可逆）

| 工具 | 为什么 |
| --- | --- |
| `generate_image` | 外部生图后端、烧配额、有 `draft`/`adopted` 生命周期 |
| `generate_bgm` | 外部音乐后端、后台排产、到货广播 |
| `list_voices` | 外部 TTS 音色库（id 是 32 位 hex，猜不出来） |
| `web_search` | 外部检索服务 |
| `view_image` | 需要把图读成模型能看的形态（含外部 URL 的安全下载与内网防护） |
| `import_asset` | 跨剧目复制素材 + 写素材表，改变剧目内容 |
| `set_craft` | **见下**，理由比"包装文件操作"强得多 |
| `read_skill` | 技能库是服务端只读目录，不在剧目文件白名单内，`read` 够不着 |

**`set_craft` 值得单独说**：它看起来最像"包裹普通文件操作"（就是改 `play.json` 的 `craft` 段），
但它的实现理由是两条硬约束——(a) `play.json` 里还躺着 `id`/`title`/`initialState` 这些引擎状态，
让模型整篇 `write` 等于把整份配置交给一次自由发挥；(b) 读改写包在 `withPlayConfigLock` 里，
与「引用即导入」「工坊文件页」共用一条队列——模型手写 `edit` 撞上另一个写者会**静默吃掉**先写的。
这两条都不是提示词能教会模型的。**结论：保留**，但把理由写进 DESCRIPTION（已具备）。

### 保留：`bash`（判据 3 的高权限侧）

默认关、按剧目手动勾。它以服务进程权限跑、不受文件白名单约束——归"需要特殊确认/审计"。

### 结论：**本轮不删除、不合并任何工具**

24 个工具全部落在判据 2 或 3，**没有一个是判据 4**。这个结果与直觉相反（工具数量看着多），
但逐个核过之后成立：数量多的原因是**领域本身有这么多语义**，不是因为有人偷懒包了一层。

## 泛化方向的真实结论

「减少定制」在这一层的正确做法**不是删工具**，而是本轮已经做的三件事：

1. **让通用工具真的通用**：`read`/`write`/`edit`/`bash` 是 pi 内建、两个角色同一套
   （早前的 `create_character` / `write_memory` 已收掉，角色卡与记忆卡回归普通文件）。
2. **把机制从提示词收回 DESCRIPTION**：让同一份说明只有一个家（P0-4 守卫生效）。
3. **长流程下沉到按需加载的 skill**（P1-9，常驻提示词减 54%）。

也就是说，**定制没有消失，而是被推到了它该在的层**——这正是「能力中立、渐进披露」的做法。
继续为删而删会踩到判据 1 与 2 的边界：删掉 `read_memory_detail` 换 `grep`，
模型就会读到别条分支的剧情，这种错误**不会报错**，只会让故事前后矛盾。

## DSH 侧对照（9 个工具）

| DSH 工具 | 独立版对应 | 说明 |
| --- | --- | --- |
| `generate_image` | `generate_image`（工坊形态） | 都是"只产候选"，采用另一步 |
| `generate_asset` | `commit_asset` + 出图 | DSH 是**一键**（生成+抠底+登记），独立版是**两步**（候选→采用） |
| `import_asset` / `cut` / `generate_bgm` / `list_voices` / `web_search` | 同名 | 语义一致 |
| `validate_play` | `get_readiness` | 检查的对象不同（DSH 检查 workspace 契约） |
| `set_stage_style` | **无对应** | DSH 独有（舞台皮肤） |

DSH 侧同样**没有判据 4 的工具**。「两宿主实现不同」已登记在 `CAPABILITY_MATRIX`，
不是待修的漂移——`generate_asset` 与 `commit_asset` 的差别是**产品选择**
（DSH 面向快速 MVP，独立版要求用户过目候选）。

## 给后续的判据

将来新增工具时，先问：**这个能力能不能拆成「通用工具 + 一段 skill」？**
- 能，且逻辑稳定 → 优先 skill（像备料流程那样，P1-9 已示范）。
- 不能（要引擎持有的状态、要原子性、要外部副作用、要分支过滤）→ 专用工具，并把理由写进 DESCRIPTION。

**判据 4 的真正适用面**是「为了提示模型下一步而造的工具」——本轮审计中一个都没有，
说明这个项目在这条线上没走偏。
