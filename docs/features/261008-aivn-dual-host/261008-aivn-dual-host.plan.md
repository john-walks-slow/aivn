# AIVN 独立版与 DSH 插件的长期维护方案

日期：2026-10-08

## 结论

不要在当前阶段二选一，也不要把两个仓库当成两套平行产品。更准确的定义是：

- `stage-ai`：AIVN 的**领域与完整产品发行线**。它负责独立运行、剧目生命周期、路线树/分支、完整工坊、独立桌面壳和最终用户产品体验。
- `dsh-aivn`：AIVN 的**DSH 宿主适配发行线**。它负责把 AIVN 能力映射到 DSH 的会话、预设、技能、工具、后台任务和客户端槽位。
- `@aivn/core`：两条线的**领域契约层**。
- `@aivn/stage`：两条线的**舞台渲染与播放层**。

因此，“主线”不是某个仓库吞掉另一个仓库，而是按层指定唯一真相源：

| 层 | 真相源 | DSH 的关系 |
|---|---|---|
| Stage DSL、解析器、IR、素材/角色数据契约、语音纯函数 | `stage-ai/packages/core` | 直接依赖，不复制 |
| 舞台 React 渲染、播放、语音播放、舞台 CSS | `stage-ai/packages/stage` | 直接依赖，不复制 |
| 独立版编排、WS、谱系、路线树、工坊线程、周目、桌面壳 | `stage-ai/apps/*` | 独立版专属 |
| DSH 预设、会话接线、SSE、工具装配、系统提示注入、DSH view | `dsh-aivn` | DSH 专属 |
| 剧作家/搭台助手的领域语义与工具契约 | 先在 `stage-ai` 记录和验证，再按宿主适配 | 不要求实现相同，但必须明确差异 |

## 当前分歧有多大

### 已经收敛的部分

2026-10-06，`@aivn/stage` 已从抽取分支合回 `stage-ai` 主线，`dsh-aivn` 当前通过 `file:../stage-ai/packages/*` 使用它。舞台组件、播放逻辑和舞台样式不应再各自演进。

`@aivn/core` 也已经是实际共享层：DSH 使用其 DSL 解析器、StageEvent、角色/素材解析、语音分句等能力。这里的复用不是概念上的，已经是构建期真实依赖。

### 仍然存在的实质分歧

| 领域 | 独立版 | DSH 插件 | 判断 |
|---|---|---|---|
| 运行时宿主 | 自有 Node server + 自有 Web SPA + Tauri sidecar | DSH Cordis 宿主 + DSH Web client | 不应统一 |
| 会话真相 | AIVN 自己的 `PlayHouse`、`LineageTree`、saves 和持久化事件 | DSH 会话日志、workspace、agent preset 和 projection | 不应互相模拟 |
| 演出传输 | 同源 REST + WS | DSH host route + SSE | 只统一 IR 语义，不统一传输实现 |
| 停止点来源 | 可由独立版编排器/工具产生 | 由 DSH 会话里的剧本标签重建并收束 | 允许宿主适配差异，但最终都转为同一 IR |
| 路线能力 | 分支、跳转、编辑、重写、CG 台账、回顾 | 线性会话优先，依赖 DSH 原生历史/fork 能力 | 不是缺失 bug，而是产品定位差异 |
| 工坊 | 独立工坊会话、线程、文件树和素材面板 | DSH 搭台助手会话、文件侧栏和技能机制 | 共享领域目标，不共享 UI/会话实现 |
| 媒体作业 | AIVN pending jobs、队列、素材台账 | DSH 原生 jobs 或同步工具调用 | 需要记录体验差异，不能假设等价 |
| 设置 | `settings.json` + 独立设置页 | DSH plugin Config + settings slot | 各自真相源 |

粗略地说，共同核心约为“领域契约 + 舞台表现 + 部分媒体/提示词语义”；不同部分已经覆盖两边最重的运行时和产品壳。继续试图让两个仓库在所有功能上逐项对齐，会制造比现在更多的双重实现。

## 用户路径与产品定位

### 独立版用户

1. 启动 AIVN 桌面应用。
2. 创建或导入剧目，进入完整剧目库。
3. 在工坊中维护世界观、角色、素材、记忆、创作参数和 Agent 能力。
4. 进入演出，在停止点做选择或自由输入。
5. 使用路线树、回顾、分支、编辑、重写、CG 台账和周目管理。

独立版的价值是“一个完整的视觉小说创作与演出产品”，不是把 DSH 的会话页复制一遍。

### DSH 用户

1. 在 DSH 中创建会话并选择剧作家或搭台助手预设。
2. 会话工作区就是剧目目录。
3. 在搭台助手会话里写入剧目文件、准备素材和调整能力。
4. 切到 AIVN 会话 view，在同一 DSH 会话中观看舞台并推进。
5. 用 DSH 原生会话历史、文件侧栏、技能机制和后台任务完成调试与迭代。

DSH 的价值是“把 AIVN 作为通用 Agent 工作流的一种专业视图和能力包”，不是复刻独立版的所有路线管理产品。

## 维护规则

### 1. 新功能先判断归属

每个新需求先回答三个问题：

1. 它是领域契约、舞台表现，还是宿主/产品功能？
2. 它是否需要独立版与 DSH 都理解同一语义？
3. 它是否依赖某个宿主的会话、权限、任务或持久化模型？

处理规则：

- **领域规则**：进入 `@aivn/core`，两边消费。
- **舞台视觉/播放规则**：进入 `@aivn/stage`，两边消费。
- **独立版的路线、周目、完整工坊和桌面体验**：只进 `stage-ai`。
- **DSH 的预设、工具装配、提示词注入、SSE、槽位和 DSH 设置**：只进 `dsh-aivn`。
- **同一用户目标但不同宿主机制**：建立一份契约/能力矩阵，分别实现，不复制另一宿主的内部状态机。

### 2. 禁止的维护方式

- 不在 `dsh-aivn` 复制 `@aivn/core` 或 `@aivn/stage` 的源码。
- 不把 `stage-ai/apps/server` 的 `PlayHouse`、`orchestrator`、`WorkshopSession` 原样搬进 DSH。
- 不为了“看起来一致”给 DSH 添加独立版路线树、saves 或 workshop threads。
- 不为了“插件简单”把独立版的领域契约降级为 DSH 私有格式。
- 不把提示词、工具描述和能力门控分别在两个仓库随意修改而不登记差异。

### 3. 跨线契约必须有单一记录

至少维护以下矩阵，放在 `stage-ai/docs/`，每次新增能力时更新：

| 能力 | 领域语义 | 独立版实现 | DSH 实现 | 是否要求行为等价 | 已知差异 |
|---|---|---|---|---|---|
| 停止点 | `stop` IR / options / placeholder | 工具或编排器 | 剧本标签 + stage tap | 是 | 来源不同 |
| 语音 | phrase / line seq / ready | WS + VoiceDirector | SSE + VoiceDirector | 核心语义是 | 背压与任务生命周期不同 |
| 生图 | 目标、候选、采用、资产落库 | pending/adoption pipeline | DSH tool/jobs pipeline | 否，需记录 | 同步/异步和确认流程不同 |
| 角色与立绘 | character/sprite identity | core + server asset layer | core + plugin asset layer | 是 | 存储入口不同 |
| 工具权限 | capability 与副作用 | server agentkit | DSH preset/tool catalog | 目标一致 | 宿主权限模型不同 |
| 提示词注入 | premise/cast/assets/craft/state | AIVN prompt assembly | DSH systemPrompt sections | 内容语义一致 | 注入时机不同 |

矩阵的目的不是要求所有行都完全相同，而是让每一处差异变成有意设计，避免“某边漏同步”与“某边偷偷漂移”混在一起。

### 4. 依赖与版本策略

短期继续采用当前本地兄弟仓依赖，但把它视为开发布局，不是长期发布契约：

- `dsh-aivn` 构建前依赖 `stage-ai/packages/core` 与 `stage-ai/packages/stage`。
- 这个依赖是**构建期依赖**，不是插件运行时依赖：esbuild 会把 `core/stage` 打进 `lib/index.js` 与 `lib/client.js`。因此改完共享包后，必须同时重建 dsh-aivn 的 `lib/`；只更新源码而不重建，或只更新 `lib/` 而没有记录输入版本，都会造成静默漂移。
- `lib/` 是 dsh-aivn 的受跟踪构建产物，改插件源码必须重新构建并提交。
- 改 `core` 或 `stage` 后，先在 `stage-ai` 完成构建、测试和版本变更，再在 `dsh-aivn` 更新依赖、记录共享包 commit/version，并跑插件 e2e。
- 在没有真实外部接收方前，不为假设的发布者急着把内部包发到公网 npm。若未来需要自包含构建，优先使用 `vendor/` tarball；只有确实需要 registry 消费时再发布版本化包。

中期应把两个共享包纳入明确的**构建输入与兼容矩阵**：

- `core` 和 `stage` 使用语义化版本；dsh-aivn 的构建记录同时保留包版本和来源 commit。
- DSH 插件锁定兼容范围，不直接跟随任意工作树；`package-lock.json` 不应长期把本机 `file:../stage-ai` 路径当成可分发契约。
- 在 dsh-aivn 的干净构建中，从固定版本包或 `vendor/` tarball 生成 `lib/`，再执行 `npm pack` 隔离安装验证。
- 共享包与 DSH 当前宿主的 React/DSH API 版本也要纳入矩阵；`@aivn/stage` 与 DSH 插件目前并非同一 React 主版本，不能只以 TypeScript 通过判断运行时兼容。
- 每次共享包变更都跑：共享包单测/构建、独立版受影响测试、DSH 的 build check 和离线 e2e。

### 5. 验证分层

共享层：

- `@aivn/core`：DSL parser、IR、素材/角色、语音纯函数的单测和 golden tests。
- `@aivn/stage`：playback、script、asset index、stage 组件相关测试。

独立版：

- server 的编排、WS、谱系、工坊、设置和资产测试。
- web 的独立版路线、工坊、导演栏和完整演出 e2e。
- desktop 只验证 sidecar 启停和打包链路。

DSH：

- plugin build / `lib` 一致性检查。
- 预设、工具面、提示词注入、SSE 重连、停止点和舞台 view e2e。
- 真后端媒体测试继续单点执行，不作为每次共享层变更的默认全量回归。

## 实施优先级

### P0：先稳定边界，不扩功能

1. 在主仓库提交本方案及能力矩阵。
2. 检查并修复当前共享包版本漂移；至少让根包、core、stage、server、web 的版本策略可解释。
3. 在两边 README/AGENTS 中明确“独立版”和“DSH 插件”的定位及不追求等价的能力。
4. 将工具权限、提示词注入、媒体生命周期差异登记为契约，优先处理已有专家检视提出的权限 profile 与 `generate_image` 语义问题。
5. 将共享包变更的双边验证写成固定清单或脚本，避免靠记忆手工同步。

### P1：降低真正的重复实现

1. 继续把纯领域逻辑下沉到 `@aivn/core`，但只下沉稳定、宿主无关的规则。
2. 保持 `@aivn/stage` 的宿主无关边界；需要宿主数据时通过 props/transport 接缝，不把 DSH 或独立版路由写入包内。
3. 对媒体能力优先抽取“领域结果与生命周期契约”，而不是直接共用整套后端。独立版可异步排队，DSH 可同步等待，但两边应共享目标、状态和错误语义。
4. 对工具和能力目录建立可生成或可校验的契约，分别产出 AIVN agentkit 与 DSH tool catalog，避免描述和权限继续漂移。

### P2：等产品方向被真实使用验证后再选主发行重点

观察以下信号后再决定投入重心：

- 独立版是否真的需要路线树、周目和完整工坊，而不是仅作为开发实验场。
- DSH 用户是否持续使用 AIVN view，以及 DSH 会话/技能生态是否显著降低调试成本。
- 两边真实 bug 的来源：领域层、舞台层，还是宿主适配层。
- 用户是否需要跨 DSH 会话与独立版剧目目录的稳定迁移。

在这些信号出现前，不建议把独立版降级成 DSH 的 demo，也不建议让 DSH 插件承担完整独立产品的所有复杂度。

## 需要接受的现实

当前维护成本仍然不低：`dsh-aivn` 已经重新实现了剧目读写、提示词、工具、媒体、语音和事件投影，不能把它误称为“只写了一个薄适配器”。但这部分重复主要来自两个不同的 Agent 宿主和持久化模型，不是简单把代码搬到共享包就能消除。

真正值得消除的重复是：

- 同一 DSL/IR/素材身份规则各写一遍；
- 同一舞台 React/播放/CSS 各维护一份；
- 同一工具权限和提示词承诺在两边无记录地漂移；
- 同一媒体资源状态在两边使用不同名字和不兼容的生命周期。

因此后续目标应是“减少无意分歧”，不是“消灭所有分歧”。
